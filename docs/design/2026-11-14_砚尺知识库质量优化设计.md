# 砚尺知识库质量优化设计

> 版本：v1 | 日期：2026-11-15 | 状态：已定稿 | 评审轮次：3 轮

## 1. 目标与范围

### 1.1 背景与问题定义

`knowledge/yanchi_ui知识库` 当前有 185 个 Markdown 文件，其中 144 个为 `K_` 知识卡、41 个为编号长文档。只读审计确认：文件格式整体可读取，没有空文件、完全重复文件或系统性 frontmatter 损坏；但存在以下影响“专家知识可信度”的问题：

1. **确定性事实错误与内部冲突**：包括 WCAG 大文本条件缺失、键盘例外被错误否定、24 列栅格被误认为可五等分、视觉 Value 被误译为“质量”。
2. **主题污染**：按主主题人工分诊约 53 篇偏题候选，涉及医疗器械、专利、政府架构、API 网关、数据治理等。该数量是复核起点，不是自动删除名单。
3. **证据链不完整**：已有 URL 级溯源，但大量采集材料只包含搜索结果标题、URL 和摘要，不能证明模型阅读过网页全文，也不能证明正文主张由该 URL 支持。
4. **语义重复与合并失真**：现有 `mergeInto` 只追加 sources，不处理新增主张、冲突或正文修订。
5. **内容完成度不稳定**：部分卡片标题承诺完整清单或构建方法，正文却只有部分项目或资料入口。正文长度本身不是质量指标。
6. **检索输入被元数据挤占**：25 篇文件的正文起点超过 TDB 前 500 字预览范围，非 Expand 检索可能只看到 frontmatter 和来源 URL。
7. **索引与作答验收失效**：TDB provenance 不匹配导致拒启；旧索引只有 162 个目标库文件，另有 23 个新增文件未入索引、11 个文件内容已变化。盲测又允许模型用“通行原则”补答，高作答分不能证明知识覆盖或检索质量。

### 1.2 总目标

将当前“自动累积、带 URL 的素材库”改造成“可验证、可检索、可回滚的专家知识发布系统”，同时完成两条工作线：

- **存量治理线**：备份与写保护 → 全量分诊 → 高风险事实修订 → 偏题隔离 → 近重复与冲突处理 → 索引及检索验收 → 发布。
- **增量防污染线**：发现权威资料 → 获取全文证据 → 主题与主张核验 → 去重和冲突复核 → 文件级索引验证 → 活跃发布 → 持续回归。

### 1.3 可判定目标

1. 活跃库中的高风险规范与事实主张，100% 具有可回查的全文证据映射。
2. 185 篇存量文件 100% 有处置记录；偏题、证据不足和待复核内容不得留在活动检索路径。
3. 磁盘、SQLite 与 TriviumDB 的文件路径和 checksum 100% 一致；不允许缺 chunk、孤儿节点或静默部分摄取。
4. Golden query 必需探针 100% 通过，隔离内容负例零命中；检索失败与真实零命中分别报告。
5. 搜索摘要不再作为“事实已核验”的证明；事实卡必须有归档全文和具体证据片段。
6. 索引不可用、状态未知、超时、预期文件未命中或版本不一致时，蒸馏发布和盲测均 fail closed。
7. 高作答分不得抵消检索失败；质量失败不关闭学习缺口、不推进学习水位。
8. 在当前四库原目录重建场景中，清空、重建、验证和必要回滚的总维护窗口不超过 30 分钟；预计超时则不得开始清空。

### 1.4 范围

包含：

- `knowledge/yanchi_ui知识库` 存量内容治理；
- 专家铸造的 harvest、distill、knowledgeWriter、learn、trial 与持续进修；
- TDB 冷库的索引规范化、provenance、重建、审计和检索评测；
- 可复用于其他专家的通用质量服务，砚尺作为首个全链路试点；
- 已实测搜索与全文取证插件的适配、回退与验收。

不包含：

- 专家人格、工作日志、热记忆算法或 LightMemo 行为调整；
- 对整个 RAGDiaryPlugin 的重写；
- 无备份的批量删除；
- 通过绕过登录、CAPTCHA、访问控制或站点限制获取资料；
- 以统一最小字数替代知识完整性判断；
- 未经用户复核的高风险事实修订或内容型合并发布。

## 2. 总体设计 / 架构

### 2.1 质量闭环

保持现有 `blueprint → harvest → distill → synthesize → trial` 主流程，不新增第六个顶层步骤。质量能力嵌入 distill、发布和 trial 内部：

```text
搜索发现
  → 材料级主题分诊
  → 全文取证与库外证据归档
  → 候选知识蒸馏
  → 单元级主题/主张/完整性检查
  → 去重、冲突和合并分类
  → 用户或规则复核
  → publishing
  → 文件级索引与 Golden 探针
  → active
  → 持续一致性与检索回归
```

核心原则：

- **原始证据与正式知识分离**：原始网页只进入证据区，不直接进入 `knowledge/`。
- **候选与活跃知识分离**：只有通过内容和索引门禁的 revision 才记为 active。
- **检索与作答分离**：分别评价检索覆盖和答案质量，不允许互相遮丑。
- **机器检查与人工判断分离**：确定性规则自动执行；用户负责高风险事实修订和内容型合并的最终发布。

### 2.2 状态模型与物理位置

发布状态必须由“物理位置 + 发布清单”共同表达，不能只写 frontmatter。

| 状态 | 物理位置 | 是否可检索 | 进入条件 |
|---|---|---:|---|
| `candidate` | `Agent/forge/runs/<jobId>/candidates/` | 否 | 蒸馏完成，尚未通过质量门禁 |
| `needs_review` | `Agent/forge/runs/<jobId>/review/` 或专家复核区 | 否 | 证据不确定、来源冲突、内容型合并、发布验证失败 |
| `quarantine` | 活动 `knowledge/` 根之外的隔离区 | 否 | 明确偏题、无支持主张、证据异常或其他硬拒绝 |
| `publishing` | `knowledge/<库名>/` 中的短暂操作态 | 待验证 | 内容门禁已通过，等待索引和探针确认 |
| `active` | `knowledge/<库名>/` + publication manifest | 是 | 内容、索引和发布验收全部通过 |
| `active-legacy` | 旧卡的审计标记 | 仅过渡 | 尚未证明通过新门禁，不得冒充已核验 |

禁止以下做法：

- 在 `knowledge/<库名>/quarantine/` 中隔离，因为 TDB 仍会递归扫描；
- 仅通过 frontmatter 写 `status: quarantine`，但不移出活动库；
- 仅通过 agent 权限白名单代替物理隔离；
- 在发布验证失败后只移动文件而不等待 TDB unlink 队列消化。

`publishing` 失败时，文件必须 demote 到 `needs_review`，等待索引删除收敛后才能重新发布。`listLibraries()` 不能用来证明隔离生效。

## 3. 详细设计

### 3.1 TDB 原目录恢复、重建与回滚

#### 3.1.1 当前根因

`VectorStoreTDB/embedding-manifest.json` 记录的 chunker SHA-256 为 `6c2b0f…`，当前 `TextChunker.js` 为 `6cf674…`。初始化在 `_prepareStoreIdentity()` 比较失败后产生 `TDB_STORE_REBUILD_REQUIRED`；非严格模式提前返回，导致 watcher、启动扫描和 meta DB 初始化均未执行，`search()` 返回空数组。

该问题不是知识文件新增或 frontmatter 导致的。不得手改 manifest 哈希冒充兼容，也不得只凭外层“初始化完成”日志判断可用。

#### 3.1.2 已确认恢复策略

采用 **D1 方案 C：备份后清空原 `storePath` 重建**。

执行顺序：

1. 在维护窗口外完成备份、耗时测算和恢复演练；记录当前代码、manifest、模型、维度、端点、语料快照和回滚配对。
2. 暂停同专家手动、自动、定期进修；取得维护独占锁，等待旧写租约排空或明确取消相关任务。
3. 备份至少覆盖知识文件、`VectorStoreTDB`、forge 运行资料及必要配置，生成路径和 SHA-256 清单。
4. 估算全量四库构建、验证和可能回滚的总耗时。**预计无法在 30 分钟内完成时，不得清空原目录。**
5. 确认备份可读取、恢复点可用后，清空原 `storePath`，以同一语料快照和当前完整索引管线全量摄取。
6. 等待摄取结束后正常 shutdown，再从磁盘重新打开，执行 §3.2 的三层审计和 Golden query。
7. 完整重启生产进程，验证所有冷库，而非只验证砚尺。
8. 任一门禁失败或达到维护窗口上限时，恢复旧 store 及与其兼容的配套代码。代码与 store 必须成对回滚。

30 分钟是清空、重建、验证和必要回滚的总维护窗口。备份和测算应先完成；不得以“重建已经开始”为由突破回滚时限。

#### 3.1.3 Provenance 扩展

manifest 增加或升级：

```json
{
  "schemaVersion": 2,
  "normalizer": {
    "name": "forge-markdown-normalizer",
    "version": "1",
    "implementationHash": "sha256:...",
    "optionsHash": "sha256:..."
  },
  "chunker": {
    "version": "sha256:...",
    "optionsHash": "sha256:..."
  }
}
```

normalizer 实现、有效配置、chunker 实现及有效 `maxTokens/overlapTokens/tokenizer` 参数均参与兼容性判断。日常语料增删仍走增量索引，不要求重建。

### 3.2 索引规范化、三层审计与 Golden 回归

#### 3.2.1 Normalizer

在 `TDBKnowledge.js` 调用 `chunkText()` 前新增纯函数：

```text
rawContent → normalizeForIndex() → chunkText()
```

处理两类已知 writer 格式：

- `K_` 知识卡：只移除首个 YAML frontmatter 中的顶层 `sources` 块，保留 title、oneLiner、type、subskill、tags 和正文；
- 编号长文档：只移除文档头部由 writer 生成的 `> 来源：` 与 `> 抓取时间：` 行。

不得误删正文 URL、代码块内容、普通 `sources:` 字段或非首个 `---`。frontmatter 结构无法确定时应显式摄取失败，不得静默回退为嵌入全部来源头。

embedding、BM25 `indexText`、`text_preview` 和 normalized chunk checksum 必须消费同一份规范化 chunks。原始文件 SHA-256 继续用于磁盘对账；`_expandHits()` 继续从 `rootPath` 回读原始全文，保证引用和抓取时间可回查。

normalized-empty、缺向量、chunk 空洞或部分摄取均为失败，不得留下旧节点冒充更新成功。

#### 3.2.2 三层一致性审计

新增冷库专用审计入口，输出机器可读报告，任一差异非零退出：

1. **磁盘 ↔ SQLite files**：可索引路径集合、原始 hash、size 一致；分别报告 new、missing、orphan、changed；队列不得有 pending/retry/processing/failed。
2. **SQLite ↔ 重算 chunks**：每文件重新执行 normalizer + chunker，核对块数、连续 `chunk_index` 和每块 hash；不允许缺向量空洞。
3. **SQLite ↔ TriviumDB**：核对 doc/chunk 节点、payload、library、source_path、chunk_index、checksum、text_preview、维度和孤儿节点。

正常关闭并重新打开后再次执行文本和向量查询，证明 BM25 与原生数据已持久化。不能只检查内存队列或 `listLibraries()`。

#### 3.2.3 Golden query

- 每个子技能至少覆盖概念、应用、边界和负例；
- 覆盖本次 23 个新增、11 个变更文件，以及其他三个冷库的跨库样本；
- 直接消费 `TDBKnowledgeManager.search()` 返回的 `sourceFile/chunkIndex/score/text`，排名评测显式 `expand:false`；
- 保留 BrowserSearch/Parallel 等结构化来源信息，不以 Markdown 反解析代替文档 ID；
- Recall、MRR、nDCG、noise 只在同一语料快照、chunker、embedding、K/alpha/minScore 下比较；
- 旧损坏索引不作为清洗前后质量提升的公平基线。

发布阈值：路径与 checksum 100% 一致，必需探针 100% 通过，隔离负例零命中。MRR/nDCG 首版先形成可信基线，后续回归不得无故下降。

### 3.3 存量 185 篇分诊、修订与合并

#### 3.3.1 分诊顺序

1. 冻结写入并生成文件、来源、主题、证据、冲突和重复候选清单。
2. 优先修订 WCAG、键盘、对比度、拖放、栅格和视觉基础概念。
3. 将偏题、证据不足和不确定内容移入活动库外对应区域。
4. 合并近重复、消解冲突、补全或降低标题承诺。
5. 灰度发布并执行索引、Golden 和回滚验收。

#### 3.3.2 风险分级

| 类型 | 处置 | 最终发布条件 |
|---|---|---|
| 高风险规范（WCAG 等） | 优先官方全文，逐条建立主张证据映射 | 用户复核批准 |
| 确定性错误（数学、术语等） | 修正或撤回，保留修订记录 | 对应回归例题通过 |
| 多约定规则（P 级、8pt、12/24 列） | 记录组织、版本、适用条件和例外 | 不再无条件给出冲突答案 |
| 不完整资料 | 补全、改题或退回待加工 | 标题与正文承诺一致 |
| 明显偏题 | 默认库外隔离，保留原因和恢复路径 | UI 负例检索零命中 |
| 经验法则 | 标为 heuristic，删除绝对化措辞 | 场景、边界和反例明确 |

不设置统一最小正文长度。定义卡可以简短；方法卡必须可执行；清单卡必须兑现数量；争议卡必须展示适用域。

#### 3.3.3 去重与合并

候选生成使用：规范化标题/正文 hash、精确 URL、向量近邻和独立 LLM 裁决。不得只凭标题相似自动覆盖。

- **纯重复且无新增主张**：合并 sources，保留旧 fetchedAt。
- **有补充、更新或正文变化**：生成 `mergeProposal`，包含旧正文、新正文、来源并集、证据和 diff，进入用户复核。
- **存在冲突**：标记 `conflicted`，不得自动选择“看起来更新”的一条。
- **跨子技能合并**：一律 `needs_review`；自动合并仅限同 subskill。

### 3.4 搜索发现与全文取证插件优先级

以下优先级来自生产 `/v1/human/tool` 对公开 WCAG 查询和 W3C Keyboard 页面的实测。延迟只作为本次基线，不作为固定 SLA。

#### 3.4.1 日常资料发现

```text
ParallelSearch → AnySearch → TavilySearch → BrowserSearch
```

| 顺序 | 插件 | 实测依据 | 定位 |
|---:|---|---|---|
| 1 | ParallelSearch | 8.82s；首条精确命中 W3C Keyboard；结构化 results[] | 质量优先主入口 |
| 2 | AnySearch | 2.49s；历史 398 份材料成功；结果较宽泛 | 快速发现和回退 |
| 3 | TavilySearch | 4.29s；W3C 内容有效，包含关键例外 | 补充发现与精确日期能力 |
| 4 | BrowserSearch | 重启后约 5s；仍有区域重定向，相关性较弱 | 独立搜索引擎回退，不作硬依赖 |

FlashDeepSearch 已禁用，彻底从 `SEARCH_TOOL_CHAIN` 与 `FORGE_ALLOWED_TOOLS` 移除。

#### 3.4.2 每周持续进修

```text
TavilySearch(start_date/end_date)
  → BrowserSearch(timeRange=week, bypassCache=true, closeTab=true)
  → AnySearch + 已有 URL 去重
```

不得让 AnySearch 的任意旧结果短路时间门禁。Tavily 精确日期与 BrowserSearch week 参数虽存在，仍需使用已知发布时间的新旧页面做时效验收后才能视为通过。

#### 3.4.3 全文证据归档

主链：

```text
UrlFetch(mode=text)
  → ParallelSearch.web_fetch(full_content=true)
  → AnySearch.extract
  → ChromeBridge
```

| 顺序 | 路径 | 实测依据 | 场景 |
|---:|---|---|---|
| 1 | UrlFetch | 4.31s，约 11,855 字符 | 默认稳健路径，PDF、动态页面和浏览器回退 |
| 2 | ParallelSearch.web_fetch | 9.60s，full_content 约 14,924 字符，errors=[] | 批量 URL、结构化字段和逐 URL 错误 |
| 3 | AnySearch.extract | 1.26s，约 12,183 字符，无截断 | 静态单页最快，可在该场景提前 |
| 4 | ChromeBridge | 重启 managed Chrome 后成功 | 复杂交互页面最后回退 |

Parallel `full_content` 必须显式为 `true`。UrlFetch 在 forge 中优先 `mode=text`，由 harvest 写入 `runs/<jobId>/evidence/`；不得直接 `download` 到 `knowledge/`。

#### 3.4.4 统一回退条件

以下均视为当前路径失败，而不是“成功但内容较少”：

- HTTP/认证/额度/429/超时；
- HTTP 200 但自然结果为空；
- CAPTCHA、`blocked=true`、异常区域重定向或 `documentGeneration` 状态错误；
- 有结果但权威来源不达标；
- 正文为空、只有应用壳、触发截断或缺少预期条款；
- 批量结果中对应 URL 出现在 `errors`；
- 时间条件未实际生效。

VSearch 的 Tavily 模式与 TavilySearch 共享后端，不得作为独立容错路径。Google 曾出现打开超时、百度曾出现会话代次错误，未在干净会话复测，因此不调整其可靠性判断。

### 3.5 质量门禁插入点与算法

#### 3.5.1 模块划分

新增 `modules/agentGateway/services/forge/qualityGate.js`，避免继续把所有规则堆入 `distill.js`。最小接口：

```text
assessMaterial({ blueprint, subskill, material }) → QualityVerdict
assessUnit({ blueprint, subskill, unit, evidenceStore }) → QualityVerdict
verifyClaims({ unit, evidenceStore, llm }) → Claim[]
classifyMerge({ unit, targetCard }) → source-only | content-revision | conflict
assertIndexReady({ manager, expectedFiles, probes }) → ReadinessReport
```

新增搜索适配层统一输出 `DiscoveryItem` 和 `EvidenceDocument`，插件差异不得泄漏到蒸馏核心。

#### 3.5.2 主题门禁

- 材料读取后、分批蒸馏前执行材料级判断；
- URL 白名单之后、任何 merge/write 之前执行单元级判断；
- 依据蓝图 `scope.responsibilities/boundaries` 和当前 subskill；
- `out_of_scope → quarantine`；`adjacent/uncertain → needs_review`；
- 不得为凑域名数量放入低相关材料；
- 自动 merge 候选和标题清单限同 subskill，跨子技能只给复核建议。

harvest 可提前写主题元数据以降低成本，但不能替代 distill 最终门禁。

#### 3.5.3 主张与证据门禁

顺序必须为：

1. URL 属于本批材料；
2. 事实或规范主张有归档全文；
3. 引文能在对应 `contentHash` 的正文中规范化精确匹配；
4. 独立校验调用判断引文是否支持标题、oneLiner 和正文关键主张；
5. 冲突、低置信或来源互相矛盾时进入 `needs_review`。

独立校验必须复用 `ctx.llm` 的包装端口，继续经过费用、取消、预算和重试护栏；不得绕过直接调用原始 LLM 端口。

标题孤证、搜索摘要孤证不得通过。`normative/factual` 需要证据；`heuristic` 必须有适用范围；`opinion` 不得写成普遍标准。标准规范优先官方原文。

#### 3.5.4 完整性与冲突门禁

按卡片类型检查，而非按字数检查：

- definition：定义、边界和必要例外；
- methodology：前置条件、步骤、输出和验证方式；
- checklist：项目数量与标题一致，每项有可判定标准；
- comparison：适用条件、取舍和反例；
- rule：组织、版本、作用域和冲突处理。

发现“七项只有四项”“方法只有目录”“P 级定义互相冲突”等情况时，补全、改题或进入 `needs_review`，不得按完整知识发布。

### 3.6 发布、索引就绪、维护锁与学习水位

#### 3.6.1 索引就绪

distill 和 trial 均执行以下合取条件：

```text
manager.initialized
AND initializationState == compatible
AND 队列已收敛
AND 每个预期文件的路径与 checksum 正确
AND 每个目标子技能的预期 sourceFile 正向探针命中
AND 内容型 merge 的新正文探针命中
```

`pendingIngestCount()` 是全局计数，只可作为辅助条件；watcher 尚未入队时短暂为零不构成成功。

索引不可用、状态未知、读取失败、超时或探针未命中时：

- distill 不落步骤成功 marker；
- 不进入 synthesize/trial；
- 候选转入 `needs_review`，保留 resume 能力；
- 已短暂进入 publishing 的文件必须 demote，并等待 unlink 收敛；
- `FORGE_INDEX_READINESS_TIMEOUT_MS` 只控制等待时间，超时是可重试错误，不是警告放行。

冒烟从“首子技能任意命中”改为“全部目标子技能的预期文件与新增内容探针”。无新材料、质量过滤后零产物和检索失败必须分别报告。

#### 3.6.2 每专家维护锁

在 `Agent/forge/<name>/` 下维护持久化 lease，字段至少包括：

```json
{
  "ownerJobId": "job_...",
  "mode": "learn | cleanup | rebuild",
  "pid": 0,
  "heartbeatAt": "ISO 8601",
  "expiresAt": "ISO 8601"
}
```

采用原子独占创建、heartbeat 和 `finally` 释放。检查位置：

- `lifelongScheduler.js` 每轮调度前；
- `service.js:startExpertLearnJob`，覆盖手动、定期和 trial 自动回填；
- 步骤执行前和 distill 发布前二次检查。

暂停时返回明确的 `FORGE_EXPERT_WRITE_PAUSED`。不得用 `archived.json` 代替维护锁。TDB 每库索引 Promise 队列不能替代 forge 文件写锁。

#### 3.6.3 学习缺口与水位

D4 采用“单卡隔离、批次需复核”：合格卡可发布，问题卡单独隔离，但存在未解决项时批次不得记为完全成功。

只有同时满足以下条件才关闭 gap、推进学习水位：

- 本次应有质量产物已 active；
- 索引验证通过；
- 若配置 retest，重测有效且达到新通过条件。

`needs_review/quarantine/failed/零合格产物` 均不关闭 gap、不推进 since。学习水位取“最后一次成功 active 发布”，不是历史最后一行记录。

### 3.7 检索证据与盲测解耦

1. `blindSearch` 遍历全部关键词，不再只使用 `keywords[0]`；记录 query、error、sourceFile 和检索证据。
2. 搜索异常不得吞成“无知识”；搜索失败与真实零命中分开。
3. 开考前检查每个非 practical 子技能的最低检索覆盖。
4. “通行原则”只能补充已有库内核心答案的缺口，不得替代零核心命中作答，不得补充新的具体数字、版本事实或可验证主张，并须逐段标注。
5. 判卷输入加入 `retrievalEvidence`，分别评价库内依据答案和通行原则补充；unsupported claims 或必需覆盖缺失约束最终 `passed`。
6. `referencePoints` 若来自模型专业常识，必须标为 general reference 或验证其库内支持，不能自动当成知识库覆盖标准。
7. 旧 regrade 没有检索正文时标为 `legacy/unverified`，不得伪造证据；新 retest 使用相同门禁。
8. `scoreGrading` 保持纯计分，最终通过与 readiness/coverage 的合取放在运行流程中，避免影响只重判旧答卷的能力。

### 3.8 测试隔离、观测与安全

#### 3.8.1 测试隔离

所有可能到达 distill 的测试显式使用临时 `knowledgeRoot`；TDB 测试同时临时化 `rootPath/storePath`。所有可能到达 synthesize 的测试显式隔离：

- `agentMapPath`
- `knowledgePolicyPath`
- `guidanceConfigPath`
- `memoryPolicyPath`
- `recallProfilesPath`

禁止测试写入生产 `Agent/forge/`、`knowledge/`、`VectorStoreTDB/`、`agent_map.json` 或 `modules/agentGateway/config/`。单元测试使用 fake LLM/search port，不访问真实 API；真实插件测试独立标记，不与默认单测混跑。

不新增生产可用的 `FORGE_QUALITY_STRICT=false` 总开关。

#### 3.8.2 重点测试

- normalizer：多行/内联 sources、CRLF/BOM、无 frontmatter、正文 URL/代码块不动、畸形头失败；
- 质量门禁：偏题、假 URL、假引文、标题孤证、跨子技能 merge、内容型 merge；
- fail-open 反转：TDB 不可用、持续未命中、索引超时不得再完成 distill/trial；
- 发布：失败 staging 不推进 revision，demote 后等待 unlink，旧 revision 可恢复；
- 检索：必需/负例/新增/变更/跨库探针、preview 与 Expand 契约；
- 盲测：高答案分低检索分必须总体不通过；
- 并发：手动/自动/定期进修互斥，清洗锁可阻断已开始但尚未发布的旧任务；
- 时间过滤：用已知发布日期的新旧页面验证 start/end/week 的真实边界。

生产模板与内置 fallback 必须同步修改，避免临时测试目录只走 fallback 而出现假绿。

#### 3.8.3 安全与不可信内容

网页、搜索摘要、PDF 和页面图均是不可信数据，不得改变系统指令、工具权限或审批规则。保留现有 secret 扫描；原始证据放在活动库外；模型只接收完成任务所需的相关片段。不得绕过登录、CAPTCHA 或访问控制获取全文。

#### 3.8.4 运行报告

每次 run 写 `quality-report.json`，至少包括材料数、全文成功率、主题分布、主张支持率、合并分类、发布/索引状态、插件尝试链、错误、耗时和规则版本。每专家保留最后成功 active revision 和趋势报告，告警必须能定位到文件、主张、查询和插件路径。

## 5. 约束与红线

1. **先备份再修改**：不得手改 manifest 冒充兼容，不得无备份清空，不得在活动句柄上热替换。
2. **30 分钟硬约束**：预计无法完成清空、重建、验证和必要回滚时，不得开始清空。
3. **摘要不是事实证据**：标题或搜索摘要只用于发现资料；事实卡必须有归档全文和证据片段。
4. **隔离必须在库外**：待复核和隔离内容不得留在 `knowledge/` 的任何可扫描子目录。
5. **未知状态不得放行**：索引失败、超时、状态未知、空结果和端口能力缺失不得共享成功语义。
6. **合并不静默覆盖**：内容型合并必须保留旧正文、新正文、证据、diff 和用户复核记录。
7. **用户复核高风险内容**：WCAG 等高风险事实修订和内容型合并由用户最终发布。
8. **检索与作答独立通过**：任何一项失败都不能由另一项高分补偿。
9. **学习成功必须真实**：needs_review、quarantine、failed 和零合格产物不关闭 gap、不推进水位。
10. **测试不得碰生产**：所有知识、索引和注册路径必须临时化，不提供生产质量总关闭开关。
11. **网页是不可信输入**：不得执行网页中的指令，不得绕过访问控制，不得将原始网页直接发布到正式库。
12. **同源故障不伪回退**：共享 Tavily 等同一后端的插件包装不计为独立容错路径。

## 8. 风险与开放问题

1. **30 分钟可行性尚未证明**：全量四库 embedding 的实际耗时和费用需先测算；不满足时限就不能开始原目录清空。
2. **全文可得性**：部分页面可能拒绝访问、需要登录或只有动态内容；失败时进入复核，不绕过限制。
3. **匿名额度与速率**：AnySearch、ParallelSearch 等匿名路径可能遇到 429 或配额变化，必须保留预算、限流和回退记录。
4. **日期过滤未验收**：Tavily start/end 和 BrowserSearch week 尚需专项时效测试，不能仅凭参数存在认定增量学习正确。
5. **浏览器稳定性**：Google 曾超时、百度曾出现会话代次错误，未在干净会话复测；BrowserSearch/ChromeBridge 始终作为可替换回退。
6. **主题分类口径**：约 53 篇只是人工初筛，最终处置以统一 scope 分类和用户复核为准。
7. **旧 regrade 证据缺口**：历史答卷没有完整检索正文，只能标 legacy/unverified，不能补造。
8. **全局 normalizer 影响**：provenance 是整个 TDB store 一份，必须执行全库回归，不能只验证砚尺。
9. **单次实测不是完整基准**：本次搜索插件测试覆盖公开 WCAG 查询和一个 W3C 页面；后续需扩充中英文、静态/动态、PDF、时间与故障样本。
10. **执行交接**：将本文档路径作为执行计划交给 `execute-plan`，即可按 milestone 开始实施；每个 milestone 通过独立验收后再合并，不在实施中静默放宽本设计的硬门禁。（2026-11-15 执行完毕：M1-M5 全部合并，每里程碑经独立评审 subagent 验证；时效验收（§6.3 末条）如实保持开放，见 docs/forge-quality-operations.md §6）
