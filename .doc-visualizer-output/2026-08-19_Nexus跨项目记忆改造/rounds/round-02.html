Nexus 跨项目记忆改造方案 R2 更新

给编码助理 Nexus 的记忆系统做改造：每个项目发一本专属日记本，通用经验单独存放——解决它在多个项目之间干活时"记忆互相串味"的问题。

2 层日记 · 通用本精简为 2 本 3 个里程碑（1 个已取消） 5 条红线 1 处核心代码改动（必做） 评审中 · 第 2 轮 · 决策已全部拍板

现在为什么不好用

问题 1：规矩定反了

Nexus 的设定文档里写着"必须脱离具体项目的局限"——它被明确要求不许记项目专属的东西。结果：这个项目怎么构建、有哪些架构约定、踩过哪些环境坑，要么没地方记，要么被硬塞进通用日记本。

问题 2：日记本按"知识类型"分，不按"项目"分

现在的通用日记不按项目区分。在 A 项目记下的内容，到 B 项目干活时照样被翻出来——这就是你说的"记忆互串"。

问题 3：回忆名单是写死的

每次开工回忆时，固定翻那几本通用日记，跟"当前人在哪个项目"完全无关。

方案一句话（第 2 轮已定）

给每个项目发一本专属日记本（命名已定：Nexus项目-<项目名>日记本，项目名写在项目根目录的 .nexus-project 标记文件里）；通用经验精简为 2 本：Nexus工程经验日记本（方法论 + 避坑 + 协作偏好）和 Nexus架构设计日记本（纯架构）。写日记前先过一道判断："这条经验离开这个项目还有用吗？"有用 → 先剥掉项目细节（泛化）再进通用本；只在本项目有意义 → 直接进项目本。通用本从此不装项目细节，互串的源头就断了。

整体结构（从上到下）

Nexus 本人（提示词里的规矩）

开工先读 .nexus-project 确认项目名 → 回忆时选对日记本 → 写完按"有没有跨项目价值"分流

Agent Gateway 工具层

4 个工具：回忆（recall_run / memory_search / context_assemble）、写入（memory_write）

白名单门禁（每本日记谁能碰）

本次改造后支持 Nexus项目-* 前缀通配：新项目零配置；配置热加载，改动立即生效不用重启

日记存储（每本日记 = 一个文件夹）

第一次写入时自动建文件夹，新项目日记零准备成本

回忆时的查找顺序

第 1 步 读项目根目录的 .nexus-project 标记文件得到项目名（文件里就一行项目名）；文件不存在时，从 git 仓库根目录名推导，并建议你补建这个文件。

第 2 步 先单独翻项目日记本（Nexus项目-<项目名>日记本）——这个项目自己的事实和决策。

第 3 步 再翻两本通用日记（工程经验 + 架构设计）——跨项目的方法论和避坑经验。

分两次翻的原因：混在一起搜时，通用经验容易靠分数盖过项目事实（详见"实现指南"雷区 5）。

第 2 轮决策后路线调整：通配符改造从"可选"升为必做并提前；首个接入项目定为 VCPToolBox；存量迁移取消。执行顺序：M1 与 M2 可并行，M3 依赖 M1+M2。

红线 1：通用日记本禁止出现项目细节

具体路径、端口、内部命名、项目特有的命令，一律不进通用本。经验必须先泛化（提炼成"哪类坑、什么打法"）才能进——这是防互串的核心纪律。

🚫

红线 2：日记名必须遵循命名规范，不许自由发挥

项目日记名统一 Nexus项目-<项目名>日记本（D3 已定）。名字错一个字就会被门禁拦下（返回 403 拒绝），自造名字等于写入失败。

🚫

红线 3：密钥和敏感信息禁止写入任何日记

不管是项目本还是通用本，API Key、密码、私钥、个人敏感数据都不许写。这是整个 Agent Gateway 的全局规矩。

🚫

红线 4：通配符只许用 Nexus项目- 这一个前缀

通配改造只允许 Nexus项目-* 这一种写法生效；不许对其他 agent 放开，也不许用更宽的模式（比如 Nexus-*）。白名单本质是安全边界，口子不能开大。

🚫

红线 5：不碰存量日记

第 2 轮已决定不做存量迁移（D5），旧日记由你自行清理。方案执行全程不许对任何既有日记做删除或批量改写。

代码改动详解（M2，第 2 轮定为必做）

核心结论：只改一个函数，全链路生效

"这个名字在白名单里吗"这个判断，集中在 modules/agentGateway/policy/mcpAgentMemoryPolicy.js 的 areDiaryNamesEquivalent 函数里。写入门禁和搜索门禁都调它——所以只改这一处，写入和搜索两条路就同时认识通配符了。

技术细节（改法与边界）▾

· 改法：在等价判断里加一条规则——名字以 * 结尾时按"前缀匹配"处理：先剥掉双方的"日记本"后缀，再比前缀。Nexus项目-* 因此能匹配 Nexus项目-VCPToolBox日记本。

· 实现注意：两个调用点传参顺序不一致（写入门禁是"白名单在前"，搜索门禁是"请求在前"），所以实现时把"带 * 的一侧视为模式"，两侧谁带 * 谁当模式。

· 边界：只允许 Nexus项目- 这一个前缀（红线 4）。可以在函数里做成通用能力，但配置里只许写这一条；也可以直接在代码里硬校验前缀白名单，更保守。

· 不用改的文件：diaryPolicyGate.js（搜索门禁）和 diaryScopeGuard.js（写入门禁）都只调上面这个函数，自动继承新能力。

· 召回配置（recall_profiles.json）保持静态不动：项目回忆走"显式指定日记本"的两个工具，不走固定名单的 recall_run，所以召回配置完全不用改。

· 测试：在 tests/agent-gateway/policy/ 下补用例——①原有精确匹配行为不变；②Nexus项目-* 能放行 Nexus项目-VCPToolBox日记本；③跨前缀（如 Nexus项目X-）拒绝；④非 Nexus项目- 前缀的通配写法（如 Nexus-*）拒绝。
