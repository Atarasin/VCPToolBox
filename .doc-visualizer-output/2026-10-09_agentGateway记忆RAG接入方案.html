agentGateway 记忆/RAG 能力接入方案（含 MCP 工具面与 skill 导出面同步）

把 RiverMemo 原生联合查询与冷知识库接进网关召回管线，让外部 MCP 客户端（Midas / FuPeng / Yui / Nexus）的召回质量与 VCPChat 对齐；既有 7 个工具不移除、只做加法（新增第 8 个 gateway_knowledge_search）。

5 个里程碑 · 13 个切片 · 20 个任务 6 条红线 已定稿 · 正式文档见 docs/design/2026-10-09_agentGateway记忆RAG接入方案.md

1. 目标与范围

背景差距（代码级核验）：① 网关召回绑定 kbm.search（RAGDiaryPlugin 的非 RiverMemo 回退路径），而生产默认已是 executeNativeRiverQuery（全 Rust 一次完成），网关模块内零引用；② 检索参数保守（MAX_RAG_K=20、默认 k=5、rerank 默认关）；③ Jev 重排因参数超限必现 400 从未生效；④ 冷知识库（TDBKnowledgeManager / TriviumDB）完全未接。

目标：外部 MCP 客户端经网关的召回质量与 VCPChat 对齐；重排真正生效；冷知识库以新工具对外并按角色隔离权限。所有接口变化只做加法。

范围外：M5 观望；不做 chatCompletionHandler 对话通道、不暴露插件工具面、不做 WorkflowKernel；不移除任何既有工具，gateway_agent_render 保持 prompt 形态。

2. 总体设计：分层与动刀位置

外部 MCP 客户端 · Claude Code / Codex / Trae / DSH 等
↓ 7+1 个 MCP 工具（既有签名不变；M4 新增第 8 个）
网关层 agentGateway · 召回管线（规则→向量→检索→合并→预算→AIMemo）+ skill 导出
↓ 端口绑定（唯一宿主耦合层，本次动刀处）
ports 层 · kbm.search（KNN 回退，保留）→ 新增 riverQuery（executeNativeRiverQuery）+ knowledgeSearch（TDB）
VCP 内核 · KnowledgeBaseManager / Rust 向量引擎 / RAGDiaryPlugin / TDBKnowledgeManager

升级发生在管线内部：M2/M3 完成后三个召回工具结果质量提升，调用方（MCP 客户端与 skill 文本）零改动。

3.1 M1 重排修复（D5·方案A）

Plugin/RAGDiaryPlugin/config.env：JevRerankMaxChoices 255→10、JevRerankMaxDocumentChars 6000→1500（≈22.5k token，压进 28k 预算）。后备：该文件已有可用传统重排配置（Q3），可关 JevAdvancedRerank 切传统路径。验证：profile 开 rerank，日志无 400、排序变化。

3.2 M2 RiverMemo 接入（核心）

  • openspec：recall profile 增加 mode: knn|river 字段与全局开关的契约。
  • riverQuery 端口：ports/ 新增窄接口；vcpPortBindings 绑定 kbm.executeNativeRiverQuery；调用形状参照 RAGDiaryPlugin.js:3307-3342（diaryNames / preparedMemoObservation（复用 applyTagBoostAsync 返回）/ topK / candidateK / coreTags / supplementalQueryVectors / hybridPlan）。
  • 失败降级（D1·方案A）：river 抛错 → 回退 searchDiary(KNN) + 审计日志与指标；KNN 路径 1.33 融合系数不动（红线 5）。
  • 管线接入（D2·方案B）：ragRetriever 语义阶段加 mode 分支；全局默认 river + 全局一键回退开关（如 AGENT_GATEWAY_RECALL_MODE=knn）；档案级覆盖不进本期。
  • 对比验证：≥20 条真实 query，覆盖 Midas/FuPeng/Yui 三类场景，river 不劣于 knn。

3.3 M3 预算与混合检索对齐（D6·方案A）

  • MAX_RAG_K 20→50、默认 k 5→8、tagBoost 暴露到 recall_profiles.json；同步审计 guidance/skill 行为描述。
  • 多查询向量：precomputeVector 阶段从 recentMessages 提取 supplementalQueryVectors。
  • BM25 混合：全文检索文件候选融入 river 查询 hybridPlan.fileCandidates（含 timeLimits 透传）。

3.4 M4 冷知识库接入

  • 端口：ports/ 绑定 TDBKnowledgeManager（server.js:114 实例化）；查询面 search / searchWithVector / searchGraphFirst / queryTql；不经 ContextBridge。
  • 新工具（D3·方案A）：gateway_knowledge_search，目录 7→8；openspec 更新 mcpOperations.json / mcpDescriptors / discoverySnapshot。
  • 权限（Q2）：付鹏观点库仅 FuPeng，其余全员；服务端按角色强制（复用 diaryScopeGuard 思路），未授权 403。
  • guidance/skill（R4）：agent_guidance.json 增补使用说明与 403 解释口径；重导出 3 个预生成包 + manifest 升版 + 签名下载回归 + secret scan。

3.5 M5 associativeDiscovery（留档）

modules/associativeDiscovery.js（跨日记拓扑回溯，基于 executeNativeRiverQuery，已有测试）。M2 稳定后另立变更纳入（D4·方案B）。

红线 1：宿主耦合隔离

一切新内核绑定只进 composition/vcpPortBindings.js；services/、core/ 出现直接内核引用即违规。

🚫

红线 2：契约变更走 openspec

MCP 工具目录（discoverySnapshot 冻结）、recall profile 字段均为已发布契约，先立正式变更再动代码。

🚫

红线 3：只做加法

不移除既有 7 个工具、不破坏既有调用方式；外部已有真实消费者（Nexus 全套在用）。

🚫

红线 4：不静默吞错

river 失败按 D1 降级并留痕（审计+指标）；禁止静默返回空/旧结果而无痕迹。

🚫

红线 5：KNN 路径 1.33 融合系数锁定

searchDiary 绑定的历史约定（「宿主搜索 API 要求历史 1.33 系数」），接入新引擎时不改旧路径该系数。

🚫

红线 6：TagMemo 只用异步门面

仅可用 applyTagBoostAsync / prepareUnifiedMemoObservation；同步 applyTagBoost 已退休（抛 TAGMEMO_JS_GRAPH_RUNTIME_RETIRED）。

总体验收（8 条，全部可判定）

  1. profile 开 rerank 后日志无 Jev HTTP 400 且召回排序可见变化（M1）。
  2. 全局 river 模式下三个召回工具调用方式不变、正常返回，日志可见 executeNativeRiverQuery；人为失败自动降级 KNN 且审计有记录（M2）。
  3. 一键回退开关切回 knn 后行为立即回退，无需代码变更（M2）。
  4. M2.S4 对比报告产出且 river 不劣于 knn（≥20 条、三类角色场景）（M2）。
  5. 档案配置 k=8 生效、上限 50 可达（大召回场景验证）（M3）。
  6. 外部 MCP 客户端可调用 gateway_knowledge_search 检索非受限库；非 FuPeng 身份查付鹏观点库得 403（M4）。
  7. 重导出的 3 个 skill 包含新工具说明、通过 secret scan、manifest 版本提升、签名下载可领取（M4）。
  8. 既有 7 个工具的既有调用（Nexus 全套）回归通过（全程）。
